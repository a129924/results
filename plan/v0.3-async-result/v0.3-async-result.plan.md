### 1.2 為什麼需要這個功能？

v0.2.0 提供了強大的同步錯誤處理與 context chain，但在現代 Python 非同步應用中缺席：

**問題場景：**
```python
# 無法在 async/await 中享受 Result 與 context chain
async def fetch_user(user_id: int):
    user = await db.fetch(user_id)  # 若失敗，拋異常或返回 None
    validated = await validate_age(user)  # 又一層異常
    # 最後無法優雅的追蹤錯誤原點（誰失敗了？為何失敗？）
```

**解決方案（v0.3.0）：**
```python
from results import AsyncResult

async def fetch_user(user_id: int) -> AsyncResult[User, FetchError]:
    async def fetch() -> Result[User, FetchError]:
        user = await db.fetch(user_id)
        return Ok(user) if user else Err(FetchError("not found"))
    
    return (
        AsyncResult.from_awaitable(fetch())
        .context("fetching user")
        .and_then_async(validate_age)
        .context("validating age")
        .and_then_async(check_permissions)
        .context("checking permissions")
    )

# 使用時 LIFO context 完整顯示
result = await fetch_user(123)
user = result.unwrap()  # 若失敗，異常將含 LIFO context chain
```

**收益：**
- **型別安全**：AsyncResult 在型別檢查中完全支援
- **調試友好**：LIFO context 跨 async 邊界完整保留
- **互通性**：async ↔ sync 無縫轉換
- **Rust 風格**：遵循 Rust 的 async Result 模式
- **零破壞**：v0.2.0 代碼無改動

### 2.2 設計決策

**決策 1：AsyncOk/AsyncErr 都實現 `Awaitable[Result[T, E]]` 介面，並保留 `resolve()` 方法**
- 原因：
  - ✅ 語法簡潔：`await async_ok` / `await async_err` 直觀且自然
  - ✅ 型別清晰：mypy 能推導 `await` 返回 `Result[T, E]`（不是裸值）
  - ✅ 習慣對齐：符合 Python async 生態（httpx、sqlalchemy 等）
  - ✅ 保留 `resolve()` 作顯式替代，減低誤用；`await x` 與 `await x.resolve()` 等價
  - ✅ 明確橋接點：在複雜型別推導或需強調「邊界」的場景下，`resolve()` 提升可讀性
- 替代方案：不實作 Awaitable，需強制呼叫 `resolve()` —— 缺乏語法流暢度，違反使用者預期
**決策 2：採用 AsyncOk/AsyncErr 變體，都實現 Awaitable 且保留 resolve()**
- 原因：
  - ✅ 型別清晰：`AsyncOk[T]` 與 `AsyncErr[E]` 在靜態檢查中表意明確，IDE 自動完成友好
  - ✅ 語法一致：直接 `await async_ok` 或 `await async_err` 回傳 `Result[T, E]`，與 sync Ok/Err 心智模型對齊
  - ✅ 對內承載完整語義：非簡單的 Ok/Err 包裝，而是承載 context LIFO 堆棧、短路規則、`*_async` 鏈式操作的 awaitable
  - ✅ 對外表現對稱：`await` 與 `resolve()` 等價回傳 `Result`；互通性無縫
  - ✅ 擴展性好：若未來需要變體專有方法，無需修改單一 AsyncResult 類
  - ✅ 符合用戶偏好「分開介面」的設計
- 替代方案：單一 AsyncResult（v0.3 初版方案）—— 考慮 API 對稱性與明確性後改採 AsyncOk/AsyncErr
**決策 3：Context chain 在 `await` 或 `unwrap_async()` 時合併，AsyncOk/AsyncErr 都遵守相同 LIFO 語義**
- 原因：
  - ✅ 保持 LIFO 格式與同步 Result 完全一致
  - ✅ context() / with_context() 無須 await（預 await 堆棧）
  - ✅ 降低使用者認知負擔；AsyncOk 與 AsyncErr 行為對稱
  - ✅ 異常訊息格式統一（若 AsyncErr 路徑拋 UnwrapError 含完整 LIFO chain）
- 實作：內部維持 `_context_stack` tuple，每次 context() 執行頭部插入
- 對稱性：AsyncOk 與 AsyncErr 都支援 context/with_context，行為一致

**決策 4：Error 型別在 `and_then_async` 自動累積為 `E | F`**
- 原因：
  - ✅ 保持同步 `and_then()` 的型別累積行為
  - ✅ 支援多層不同 error 型別的鏈
- 實作：需明確泛型變數與 overload 簽名

**決策 5：不做的事（明確邊界）**
- ❌ 不支援 `trio`、`gevent` 等替代 async 運行時（專注 asyncio）
- ❌ 不引入 async context manager（`async with`）—— 未來版本可加
- ❌ 不提供自動 sync → async 轉換（用戶顯式調用 `from_result()` 更清楚）

### 2.3 技術方案

- **框架/庫：** 標準庫 `asyncio`，無外部依賴（mypy 與 pytest-asyncio 在 dev 依賴）
- **非同步策略：**
  - AsyncResult 本身 `@dataclass(frozen=True)` 存儲 `Awaitable[Result[T, E]]`
  - 每個 async 方法（如 `map_async`, `and_then_async`）返回新 AsyncResult，内部含新的 awaitable
  - 短路評估（Short-circuit）：Err 分支無須執行後續 callable
- **型別簽名：**
  - 使用 TypeVar: `T = TypeVar("T")`, `E = TypeVar("E")`, `U = TypeVar("U")`, `F = TypeVar("F")`
  - Overload 處理不同簽名場景（如 `and_then_async` 可接受 sync 或 async callable）
  - 保持與 Result ABC 型別一致性
- **集成點：**
  - 與 Result ABC 無直接依賴（AsyncResult 獨立層）
  - 互操作：`from_result()` 用於升級同步 Result，`await result` 或 `.resolve()` 回到 Result
  - 例外保留：`unwrap_async()` 於 Err 路徑拋 UnwrapError（與同步一致）

## 6. 風險與假設

### 6.1 假設

- [x] Python 3.10+ 已正確安裝
- [x] mypy 與 ruff 已配置（繼承 v0.2.0）
- [x] pytest + pytest-asyncio 環境正常
- [x] uv 可用於依賴管理
- [x] asyncio 為唯一支援的 async 運行時

### 6.2 風險識別

**風險 1：型別檢查的誤導性（Error 型別累積）**
- 等級：Medium
- 描述：mypy 可能無法正確推導 `and_then_async` 中的 `E | F` 型別累積
- 緩解：使用 Overload 與明確泛型變數；複雜情況下提供 type stub（.pyi）
- 指標：mypy --strict 0 errors，包含累積型別檢驗

**風險 2：不支援其他 async 運行時（trio、gevent）**
- 等級：Low
- 描述：AsyncResult 目前僅設計用於 asyncio
- 緩解：明確文檔註記；未來版本評估 anyio 適配
- 指標：README 清晰說明 asyncio 前提

**風險 3：Context chain 複製成本**
- 等級：Low
- 描述：每次 context() 建立新 tuple，深度鏈可能性能衝擊
- 緩解：接受 tuple 複製；文檔提醒避免 1000+ level context；未來評估惰性評估
- 指標：基準測試：10-level chain < 1µs

**風險 4：忘記 await AsyncResult**
- 等級：Low
- 描述：使用者可能誤用 AsyncResult 而未 await
- 緩解：
  - 實作 `__await__()` 讓 type checker 警告遺漏
  - 高層次文檔強調「must await」
  - 清晰的 docstring 與範例
- 指標：類型提示與 IDE 輔助明確警告

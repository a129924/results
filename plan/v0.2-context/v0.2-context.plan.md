### 1.2 為什麼需要這個功能？

v0.1.0 可以正確處理錯誤，但在複雜操作鏈中缺少**執行上下文**追蹤：

**問題場景：**
```python
# v0.1.0 - 缺少 context
result = (
    fetch_user(1)
    .and_then(validate_age)
    .and_then(check_permissions)
    .unwrap()
)
# Error: UnwrapError("Called unwrap on Err", ValueError(...))
# ❌ 不知道在哪一步失敗了
```

**解決方案（v0.2.0）：**
```python
# v0.2.0 - 完整 context
result = (
    fetch_user(1)
    .context("fetching user")
    .and_then(validate_age)
    .context("validating age")
    .and_then(check_permissions)
    .context("checking permissions")
    .unwrap()
)
# Error: UnwrapError with chain:
# [checking permissions]
# [validating age]
# [fetching user]
# ValueError(...)
# ✅ 清楚知道失敗的路徑
```

**收益：**
- **調試友好**：完整的執行上下文鏈
- **生產可用**：快速定位問題根源
- **Rust 風格**：遵循 anyhow 的 LIFO 堆棧設計
- **零開銷選項**：不用 context 時行為不變

### 2.3 Result ABC 契約更新

根據契約式設計原則，Result ABC 需要新增 4 個抽象方法（排除 Ok/Err 內部差異）：

```python
# src/results/core/base.py 新增

@abstractmethod
def inspect(self, f: Callable[[T], None]) -> "Result[T, E]":
    """Inspect success value for debugging, return unchanged.
    
    - Ok[T]: 執行 f(value)，返回 self
    - Err[E]: 返回 self unchanged
    """
    ...

@abstractmethod
def inspect_err(self, f: Callable[[E], None]) -> "Result[T, E]":
    """Inspect error value for debugging, return unchanged.
    
    - Err[E]: 執行 f(error)，返回 self
    - Ok[T]: 返回 self unchanged
    """
    ...

@abstractmethod
def context(self, msg: str) -> "Result[T, E]":
    """Push context message to chain (eager).
    
    - Err[E]: 推入 context 到 _context_chain，返回新 Err
    - Ok[T]: 返回 self unchanged
    """
    ...

@abstractmethod
def with_context(self, f: Callable[[], str]) -> "Result[T, E]":
    """Push lazy context (delayed evaluation).
    
    - Err[E]: 調用 f() 獲取 msg，委託給 context()，返回新 Err
    - Ok[T]: 返回 self unchanged
    """
    ...
```

**為什麼在 ABC 中定義？**
- ✅ 契約明確：所有 Result 實現都必須支持這些方法
- ✅ 類型安全：用戶在 `Result[T, E]` 引用上可安全調用
- ✅ IDE 支持：自動補全和類型檢查完整

**實現分佈：**
- Ok: `inspect()` → 執行，其他三個 → self
- Err: `inspect_err()` / `context()` / `with_context()` → 執行邏輯，`inspect()` → self

---

### 2.2 設計決策

**決策 1：Context Chain 採用 LIFO 堆棧式**
- 原因：符合 Rust anyhow 的 `context()` 行為，最新 context 最先看到
- 實現：tuple 頭部插入 `(msg, *self._context_chain)`
- 優點：
  - ✅ 調試時最重要的信息最先看到
  - ✅ 符合堆棧調用順序
  - ✅ 與 Rust anyhow 100% 兼容

**決策 2：區分 `context()` 和 `with_context()`**
- 原因：提供 eager 和 lazy 兩種 context 載入方式
- `context(msg: str)`：立即推入（靜態）
- `with_context(f: Callable[[], str])`：延遲推入（動態）
- 優點：
  - ✅ 靜態 context 無開銷
  - ✅ 延遲 context 支持動態計算（如時間戳）
  - ✅ 符合 Rust anyhow API

**決策 3：`inspect()` 和 `inspect_err()` 純 debug 工具**
- 原因：調試時檢查中間值而不改變流程
- 特點：
  - ✅ 返回 self unchanged
  - ✅ callable 不能改變 Result
  - ✅ 遵循 Rust Iterator::inspect() 模式

**決策 4：不實現 `map_err_context()`**
- 原因：可用 `context().map_err()` 的組合替代，保持 API 簡潔
- 示例：
  ```python
  # 而不是 map_err_context(msg, f)
  result.context("processing").map_err(transform_error)
  ```

**決策 5：`_context_chain` 字段默認值為空 tuple**
- 原因：向後相容性（v0.1.0 創建的 Err 行為不變）
- 實現：`_context_chain: tuple[str, ...] = ()`

## 8. 設計決策記錄

### 為什麼選擇 LIFO 堆棧？

```python
# Rust anyhow 的行為
result
    .context("operation A")         // 第一個
    .and_then(lambda x: risky_b(x).context("operation B"))
    .and_then(lambda x: risky_c(x).context("operation C"))
    .unwrap()

// 如果在 C 失敗，顯示順序：
// operation C (最新，最相關)
// operation B
// operation A (最舊，最根本)

// 這是 LIFO（堆棧）順序 - 用戶最關心的信息最先看到
```

### 為什麼不用 `map_err_context`？

```python
// ❌ 複雜
result.map_err_context("msg", lambda e: transform(e))

// ✅ 簡潔且組合性更好
result.context("msg").map_err(lambda e: transform(e))
```

### 為什麼 `with_context` 用 Callable？

```python
// 支持延遲計算（如時間戳、環境變量）
result.with_context(lambda: format("Error at {}", now()))

// 同時支持靜態（via context()）
result.context("Error at initialization")
```

    """Push context message to chain (eager)."""

    """Push lazy context (delayed evaluation)."""

    """Inspect error for debugging, return unchanged."""

# Ok[T] 新方法

    """Inspect success value for debugging, return unchanged."""
